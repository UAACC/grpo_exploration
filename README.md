# GRPO Exploration

## What This Project Does

Group Relative Policy Optimization (GRPO) is a reinforcement learning method for improving LLMs after pretraining. Instead of supervised fine-tuning on correct answers, GRPO generates multiple completions for each problem, scores them with a reward function, and updates the model to favor higher-reward completions over lower-reward ones within each group.

This codebase studies **offline GRPO**: can we skip the expensive online generation step by using pre-collected completions from a stronger teacher model? We implement nine training methods (described below), evaluate them on four math benchmarks, and provide tooling to reproduce every experiment.

**The setup**: a small student model (Qwen2.5-0.5B-Instruct, 27% on MATH) learns from rollouts generated by a larger teacher (Qwen2.5-Math-7B-Instruct, 75% on MATH). Each method represents a different strategy for using the teacher's rollouts to improve the student.

## Pipeline Overview

Every experiment follows four steps. The tooling is designed so that steps 2 through 4 work for any registered dataset without code changes.

```
Step 1: Register a dataset        shared/datasets_registry.py (one-time, ~15 lines)
Step 2: Generate teacher rollouts  shared/generate_rollouts.py → JSONL file on disk
Step 3: Train a method             Method-specific train.py → LoRA checkpoint on disk
Step 4: Evaluate                   shared/eval_unified.py → greedy accuracy, pass@1, pass@16
```

### Step 1: Register a Dataset

`shared/datasets_registry.py` is the single source of truth for all dataset metadata. Each entry specifies where to find the data, how to format prompts, and how to check answers.

Currently registered:

| Dataset | Name in registry | Train problems | Test problems | Difficulty | Answer format |
|---------|-----------------|----------------|---------------|------------|---------------|
| MATH-500 | `math` | 12,000 | 500 | Hard (competition math) | `\boxed{}` LaTeX |
| GSM8K | `gsm8k` | 7,473 | 1,319 | Easy (grade school) | `####` numeric |
| SVAMP | `svamp` | 700 | 300 | Easy (elementary word problems) | Numeric |
| ASDiv | `asdiv` | 1,844 | 461 | Easy to medium (grades 1 through 6) | Numeric (units stripped) |

To add a new dataset, add one `_register(DatasetConfig(...))` block to the registry. This gives the new dataset access to the entire pipeline (rollout generation, all training methods, unified evaluation) without modifying any other file.

### Step 2: Generate Teacher Rollouts

The teacher model generates N completions per training problem using vLLM. The completions are stored in a JSONL file with per-token log-probabilities and token IDs, which offline training methods read during training.

```bash
# Submit via SLURM (recommended)
DATASET=svamp sbatch shared/run_generate_rollouts.sh

# Or run directly
python shared/generate_rollouts.py \
    --dataset svamp \
    --teacher_model /path/to/Qwen2.5-Math-7B-Instruct \
    --output_path /scratch/mrli/rollouts/svamp_teacher/rollouts.jsonl \
    --num_generations 5 \
    --temperature 0.7
```

For datasets without a proper train split (like ASDiv, which only has a validation set), pass `--manual_split train` to create a deterministic 80/20 split.

Each line of the output JSONL contains one problem with N completions:
```json
{
  "question_id": 0,
  "original_problem": "There are 87 oranges and 290 bananas...",
  "ground_truth_answer": "145",
  "system_prompt": "Please solve this math problem step by step...",
  "dataset_type": "svamp",
  "runs": [
    {
      "run_id": 0,
      "response": "To determine the number of bananas in each group...",
      "extracted_answer": "145",
      "logprobs": [-0.12, -0.34, ...],
      "completion_ids": [1234, 5678, ...]
    }
  ]
}
```

### Step 3: Train

#### Offline methods (read from rollout JSONL, no online generation)

These methods train on pre-collected teacher rollouts. They do not load the HF dataset or generate student completions during training, making them faster but off-policy.

```bash
METHOD=bc              DATASET=svamp sbatch shared/run_train_offline.sh   # Behavioral cloning (all completions)
METHOD=bc_correct      DATASET=svamp sbatch shared/run_train_offline.sh   # BC on correct completions only
METHOD=offline_grpo    DATASET=svamp sbatch shared/run_train_offline.sh   # Offline GRPO with IS correction
METHOD=dg_offline      DATASET=svamp DG_ETA=0.5 sbatch shared/run_train_offline.sh  # DG-offline with eta=0.5
```

Hyperparameters (learning rate, epochs, batch size, LoRA config) are set per dataset inside `shared/run_train_offline.sh`. Override any of them with environment variables.

#### Hybrid methods (offline teacher gradient + live student baseline)

These methods train the gradient on pre-collected teacher rollouts (like offline GRPO) but compute the per-problem student baseline by sampling K_s completions from the current LoRA-merged policy at every training step. The baseline drifts as the student improves; no precompute step required.

```bash
DATASET=svamp sbatch dr_mixture_grpo/run_dr_mixture.sh                                # Dr.Mixture-GRPO
DATASET=svamp ETA=1.0 sbatch dr_mixture_grpo/dr_dg_mixture/run_dr_dg_mixture.sh      # Dr.DG.Mixture (DG gate on Dr.Mixture A)
```

Key env vars: `K_S` (default 5, samples per qid per step), `BASELINE_TEMP` (0.7), `MAX_STEPS` (-1 for full epoch). `ETA` is the DG gate temperature for the Dr.DG.Mixture variant.

#### Online methods (generate student completions during training via vLLM)

These methods generate fresh student completions at each training step. They require the HF dataset to be cached (for prompts) and use vLLM in colocate mode on the same GPUs.

```bash
cd online_grpo
accelerate launch --config_file configs/accelerate_ddp_4gpu.yaml \
    train.py \
    --dataset_type svamp \
    --output_dir /scratch/mrli/checkpoints/online_grpo_svamp \
    --num_generations 5 \
    --num_train_epochs 15 \
    --per_device_train_batch_size 5 \
    --gradient_accumulation_steps 2
```

Mixture methods combine online student generation with offline teacher rollouts:

```bash
cd mixture_grpo

# Mixture A: unified advantage normalization over student + teacher
accelerate launch --config_file ../offline_grpo/configs/accelerate_ddp_4gpu.yaml \
    method_A_unified/train.py \
    --dataset_type svamp \
    --teacher_rollout_path /path/to/rollouts.jsonl \
    --output_dir /scratch/mrli/checkpoints/mixture_A_svamp

# Mixture B: separate online + offline losses with weight lambda
accelerate launch --config_file ../offline_grpo/configs/accelerate_ddp_4gpu.yaml \
    method_B_weighted/train.py \
    --dataset_type svamp \
    --teacher_rollout_path /path/to/rollouts.jsonl

# DG-Mixture: online GRPO + DG-gated offline teacher loss
accelerate launch --config_file ../offline_grpo/configs/accelerate_ddp_4gpu.yaml \
    dg_mixture/train.py \
    --dataset_type svamp \
    --teacher_rollout_path /path/to/rollouts.jsonl \
    --dg_temperature 0.5 \
    --dg_offline_weight 0.3
```

All training scripts accept `--dataset_type` with any name from the dataset registry.

### Step 4: Evaluate

The unified eval script computes three metrics for any registered dataset:

1. **Greedy (temp=0.0)**: deterministic argmax decoding, 5 runs averaged. This is the deployable accuracy.
2. **pass@1 (temp=0.6)**: accuracy of a single sample drawn at temperature 0.6. Lower than greedy because sampling adds randomness.
3. **pass@16 (temp=0.6, oracle)**: fraction of problems where at least one of 16 samples is correct. Requires knowing the correct answer to select the right sample. Not deployable, but diagnostic for what the model's distribution contains.

```bash
# Run all three metrics
DATASET=svamp MODEL=/scratch/mrli/merged/bc_svamp MODE=both sbatch shared/run_eval.sh

# Greedy only (faster)
DATASET=math MODEL=/path/to/model MODE=greedy RUNS=5 sbatch shared/run_eval.sh

# With LoRA merging (for unmerged checkpoints)
DATASET=math MODEL=/path/to/lora BASE=/path/to/base MERGE=1 sbatch shared/run_eval.sh
```

Or directly:
```bash
python shared/eval_unified.py \
    --model_path /path/to/model \
    --dataset svamp \
    --mode both \
    --runs 5 \
    --n_samples 16 \
    --temperature 0.6
```

## Methods

### Behavioral Cloning (BC)

Pure supervised learning on teacher completions. Minimizes cross-entropy on the completion tokens (prompt tokens are masked). The simplest baseline: if this doesn't help, the data itself isn't providing useful signal.

Directory: `bc/`. Training script: `bc/train_bc.py`. Use `--filter_correct_only` to train on correct teacher completions only.

### Offline GRPO

Off-policy GRPO using importance-sampling (IS) correction. Computes π_student/π_teacher for each token, clips the ratio PPO-style, and applies the GRPO advantage. Requires the teacher's stored log-probabilities.

Directory: `offline_grpo/`. The trainer (`offline_grpo/trainer.py`) extends TRL's GRPOTrainer by overriding `_generate_and_score_completions()` to load pre-computed rollouts instead of generating online.

### DG-Offline (Delightful Policy Gradient)

Replaces the IS ratio with a sigmoid gate on "delight" = advantage × surprisal, where surprisal is computed under the student's own policy. The gate amplifies updates from surprising teacher successes (gate near 1) and suppresses updates from surprising teacher failures (gate near 0). No behavior policy log-probabilities required.

Based on Osband (2026), "Delightful Distributed Policy Gradient" (arXiv:2603.20521). Full technical details in `docs/dg_offline/technical_reference.md` (knowledge hub at `docs/dg_offline/`).

Directory: `DG-offline/`. Key hyperparameter: `--dg_temperature` (eta) controls gate sharpness.

### Dr.Mixture-GRPO

Replaces the within-group GRPO advantage `(r − mean_group) / (std_group + ε)` with `A = r_teacher − r_mean_student(qid)`, drops the `/std` normalization (Dr. GRPO, [arXiv:2503.20783](https://arxiv.org/abs/2503.20783)), and recomputes `r_mean_student(qid)` **live every training step** by sampling K_s completions from the current LoRA-merged policy and scoring them with Math_Verifier. The intent is twofold: (a) sidestep the 85–94 % `A=0` pathology that plain GRPO hits on zero-variance teacher rollout groups, and (b) make the baseline track policy drift rather than a one-time snapshot.

The loss reduces to `−A · log π_student` by setting `old_per_token_logps = current_per_token_logps`, which neutralizes TRL's stock IS ratio and PPO clip. Inherits directly from `trl.GRPOTrainer`; no `_compute_loss` override.

Directory: `dr_mixture_grpo/`. Key hyperparameters: `--K_s` (samples per qid per step, default 5), `--baseline_temperature` (sampling temp for the student baseline, default 0.7).

### Dr.DG.Mixture

The DG-Offline sigmoid gate applied on top of Dr.Mixture's live advantage. Loss = `−sigmoid(A · surprisal / η) · A · log π_student` with `A` from Dr.Mixture and surprisal computed under the current policy on the teacher completion.

Implemented as a thin subclass of `DrMixtureGRPOTrainer` (no duplicate generation logic). Note: existing DG `eta` values were calibrated for group-normalized advantages in `[-1, 1]`; Dr.Mixture `A` is on the raw reward scale (~`±1` GSM8K/SVAMP/ASDiv, `±2` MATH), so a new sweep is needed.

Directory: `dr_mixture_grpo/dr_dg_mixture/`. Key hyperparameter: `--dg_temperature` (eta).

### Online GRPO

Standard on-policy GRPO. The student generates its own completions at each step via vLLM, then optimizes toward higher-reward completions. No teacher rollouts needed. This is the performance ceiling that offline methods aim to match.

Directory: `online_grpo/`. Uses TRL's GRPOTrainer with vLLM colocate mode.

### Mixture A (Unified)

Merges online student completions and offline teacher completions into a single group for joint advantage normalization. Both student and teacher completions contribute to the same group mean and standard deviation.

Directory: `mixture_grpo/method_A_unified/`.

### Mixture B (Weighted)

Computes separate losses for online student completions and offline teacher completions, then combines them: `L = L_online + λ × L_offline`. Each loss has its own advantage normalization.

Directory: `mixture_grpo/method_B_weighted/`.

### DG-Mixture

Combines online GRPO for student rollouts with DG-gated loss for teacher rollouts in a single training step. The teacher loss uses the same sigmoid gate as DG-offline, while the student loss is standard PPO-clipped GRPO.

Directory: `mixture_grpo/dg_mixture/`. Design document: `docs/dg_offline/plans/dg_mixture_design.md`.

## LoRA Configuration

All methods use LoRA for parameter efficiency. Only low-rank adapter weights are trained (~3.4% of total parameters), while the base model is frozen. The frozen base model also serves as the reference policy for the KL penalty via `model.disable_adapter()`, so no separate reference model copy is needed.

| Setting | Value |
|---------|-------|
| Rank (r) | 32 |
| Alpha (α) | 32 |
| Target modules | `all-linear` |
| Scaling factor (α/r) | 1.0 |
| Dropout | 0.05 |
